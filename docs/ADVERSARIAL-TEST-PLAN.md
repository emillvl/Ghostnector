# Adversarial test plan

The goal of this phase is not to accumulate passing tests. It is to **try to make `Protected` false
while Ghostnector still believes it is true**, and to classify what is observed without flattery.

Every test below therefore has: an initial state, an injected action or fault, an observation point
that is **not Ghostnector**, an expected result, the exact condition that counts as failure, the state
transition Ghostnector should make, and whether fail-closed enforcement must activate.

Nothing here replaces `PROTECTION-CLAIMS.md`; each test names the claims it exercises.

## 1. Observation points

Ghostnector is never the sole source of evidence about Ghostnector.

| ID | Point | What it can see | Status |
|---|---|---|---|
| O1 | `gh-outside` namespace, on the far side of a veth | packets and datagrams that actually left the namespace under test | **exists** |
| O2 | Recording HTTP endpoint in `gh-outside` | whether a request arrived, and from which address | to add (small) |
| O3 | Recording UDP endpoint in `gh-outside` | whether a datagram arrived at all | **exists** |
| O4 | Kernel state read directly (`nft list ruleset`, `ip route`, `conntrack`) | the policy as the kernel has it, never as Ghostnector reports it | **exists** (used ad hoc) |
| O5 | Journal and state files read directly | what was persisted, independently of the running daemon | **exists** (used ad hoc) |
| O6 | External vantage (IP echo, packet counter, canary authoritative) | what the ISP and the internet see | **M7** |
| O7 | Process exit status, logs, `ghostnector status` | supporting evidence only — never the sole evidence for a claim | **exists** |

**Not an observation point:** interface byte counters. An earlier version of the policy test used them
and reported a 250-byte "leak" from a policy that was working. The bytes were IPv6 link-local and
multicast control traffic from the veth. Byte counters cannot distinguish "the policy failed" from
"the link was noisy", so they are not a leak oracle.

## 2. Classification

Every suspicious observation ends in exactly one of these, with enough evidence to reproduce it.

| Class | Meaning | Required evidence |
|---|---|---|
| **CPT — Confirmed prohibited traffic** | traffic crossed a boundary that `PROTECTION-CLAIMS.md` says must not be crossed | the capture (packet or datagram, with 5-tuple and timestamp), the observation point, Ghostnector's state at the time, and the claim it contradicts |
| **EEC — Expected exempt or control traffic** | traffic occurred and is permitted by the documented model | the exemption or the control-traffic entry it corresponds to, by name |
| **INC — Inconclusive / noise** | the observation cannot establish either condition | what would have been needed to reach a conclusion |

Two rules:

- **Nothing is silently whitelisted to make a test pass.** A new kind of traffic observed at a
  boundary is a CPT or an INC until it is written into the control-traffic inventory below.
- **INC never becomes CPT, and INC never becomes a pass.** A test whose observation is INC has failed
  to test anything, and is recorded as such rather than as green.

### Control traffic that is expected, by name

| Traffic | Why it is expected | Documented as |
|---|---|---|
| DHCP client (UDP 68 → 67) | the link must survive | exemption PC-09, `dhcp-client` |
| Tor's own egress to relays, authorities, bridges | it cannot go through itself | exemption PC-09, `system-user:tor` |
| Loopback traffic (including the chokepoint's upstream) | it never leaves the machine | PC-01 scope |
| The verification's own probes: UDP to the check endpoint (**must not leave**), HTTP through the policy (**leaves via Tor**), canary to the chokepoint | they are the checks | PC-02, PC-06, PC-03 |
| ARP / NDP on the test link | link-local control | none: it must be classified, not ignored |
| IPv6 router solicitations, MLD reports | link-local control from the veth | none: the cause of the earlier false positive |
| ICMP errors generated by this machine's own kernel in response to a rejected packet | delivered to the local sender, not sent out | PC-02 (the rejection rule) |

## 3. Steady-state traffic

Boundary: **O1/O3** (outside namespace). Kernel state: **O4**. Externally visible destination:
whatever the test provides.

| ID | Initial | Injected action | Observed from | Expected | Fails if | State after | Fail-closed |
|---|---|---|---|---|---|---|---|
| AS-1 | `Protected` (Tor mode) | protected uid opens TCP to a listening endpoint outside | O1 | the endpoint is reached **through Tor only**; no segment to the destination is seen from the inside | any TCP segment from the protected uid arrives at the destination addressed directly | `Protected` throughout | no |
| AS-2 | `Protected` | protected uid sends UDP to a recording endpoint | O3 | no datagram arrives; the sender gets a fast refusal | a datagram arrives, or a reply reaches the sender | `Blocked` within one interval | **yes** |
| AS-3 | `Protected` | protected uid connects to a public IPv6 address | O1 (v6-capable link) | no IPv6 packet arrives; the attempt fails | any IPv6 packet from the protected uid arrives | `Blocked` within one interval | **yes** |
| AS-4 | `Protected`, IPv4-only link | protected uid connects to an IPv6 address | O1 | attempt fails | — | `Protected` | no |
| AS-5 | `Protected` | protected uid queries a hard-coded foreign resolver (`udp/tcp 53` to an address outside) | O1/O3 + O3 canary | the query is answered by the configured upstream, and nothing arrives at the foreign resolver | a port-53 datagram arrives at the foreign resolver's boundary | `Blocked` within one interval | **yes** |
| AS-6 | `Protected` | an application resolves through the system resolver and connects | O1 + O3 | resolution is answered by the chokepoint's upstream; the connection goes through the policy | a query arrives at a resolver other than the configured upstream | `Blocked` within one interval | **yes** |
| AS-7 | `Protected` | an application that ignores the system resolver (its own DoH/DoT/plain resolver) runs | O1/O3 | its traffic is carried by the policy (it cannot reach anything directly); a *plain* query to port 53 is redirected | a port-53 datagram, or any prohibited egress, arrives at the boundary | unchanged unless a claim is broken | only if a claim breaks |

**Why AS-4 is a test at all:** it must come out INC, not pass. A machine with no IPv6 connectivity
cannot demonstrate that IPv6 is denied, and recording that as a pass would be exactly the kind of
overstatement this phase exists to prevent.

## 4. Lifecycle transitions

The transition windows matter as much as steady state. A traffic storm runs from a protected uid for
the whole window; the boundary is watched continuously.

| ID | Initial | Injected action | Observed from | Expected | Fails if | State after | Fail-closed |
|---|---|---|---|---|---|---|---|
| AL-1 | `Off` | traffic storm starts, then `connect` | O1/O3, continuously | nothing prohibited leaves at any point; the machine is denied before anything is opened | one prohibited packet during the window | `Degraded` → `Protected` | n/a |
| AL-2 | `Off` | `connect` while the storm runs, Tor bootstrap is slow | O1/O3 | during bootstrap the machine is denied; the storm's traffic does not escape *and does not reach Tor either* | any egress during bootstrap | `Applying` → `Degraded` | **yes** (by ordering) |
| AL-3 | `Degraded` (applied, unverified) | configured checks pass | O7 + O1 | the claim is made only after the evidence, not before | `Protected` shown before a check passed | `Degraded` → `Protected` | no |
| AL-4 | `Protected` | `disconnect` while the storm runs | O1/O3 | nothing prohibited leaves; afterwards traffic flows normally because the policy is gone | a prohibited packet after the policy was removed while the state still claimed protection | `Protected` → `Off` | n/a |
| AL-5 | `Protected` | `core` is asked to shut down, then the storm runs | O1/O3 | the storm keeps behaving as it did while protected (the policy is still there) | any change in confinement | unchanged | n/a |
| AL-6 | `Protected` | the whole machine reboots with intent persisted | O1/O6, from before the network is up | no packet from a protected scope leaves before the policy is present | one packet observed before the policy exists | `Blocked` after boot | **yes** |
| AL-7 | `Protected` | `panic` while the storm runs | O1/O3 | the machine is denied within one atomic transaction; the storm stops | one prohibited packet after `panic` returned | `Blocked` | **yes** |

## 5. Process failures

Each failure is injected at a controlled point, and the kernel is then inspected **directly** (O4).

| ID | Initial | Injected action | Observed from | Expected | Fails if | State after | Fail-closed |
|---|---|---|---|---|---|---|---|
| AF-1 | `Protected` | `SIGKILL` Tor | O1/O4 | the policy is unchanged; protected traffic stops; nothing reaches a destination | any prohibited packet at the boundary | `Blocked` (or `Degraded` until the next check) | **yes** |
| AF-2 | `Protected` | `SIGKILL` the DNS relay (the chokepoint) | O4 + O3 | resolution stops; no port-53 packet leaves | a port-53 datagram at the boundary | `Blocked` within one interval | **yes** |
| AF-3 | `Protected` | `SIGKILL` `core` | O4 + O1 | the policy is still in the kernel; protected traffic is still confined; the CLI cannot be asked anything | any loosening coincident with the death | unreportable (nobody can be asked) | **yes** |
| AF-4 | `Protected` | `SIGKILL` `netd` | O4 | the policy is still in the kernel (the helper wrote it, the kernel holds it) | any loosening | unchanged until `netd` returns | **yes** |
| AF-5 | `Protected` | `netd` is unavailable when the boot guard runs | O4 | the boot guard applies the helper's own copy | nothing applied | `Blocked` after boot | **yes** |

**AF-3 is the important one to read correctly.** `ghostnector: cannot reach the control plane` is not
evidence of a leak and must never be displayed as one; the *only* valid observation is O4 plus O1.

| AC-2 | `Off` | the intent journal is absent, then boot | O4 | nothing is applied; the machine is open because nothing was requested | a policy appears from nowhere | `Off` | no |

| AC-5 | `Protected` | one rule inserted that permits traffic **no check exercises** (`tcp dport 8443 accept`) | O4 + O1 | **expected to be missed today.** This is gap G3; the test exists to demonstrate it, not to pass it | the test quietly passes | `Protected` (wrongly) — recorded as an open gap | no |
| AC-6 | `Protected` | stale persisted state (a journal saying protected while the kernel is empty), then `core` starts | O4 + O7 | `core` applies the fail-closed baseline and reports `Blocked` | the state reports `Off` or `Protected` | `Blocked` | **yes** |

## 7. Network changes

| ID | Initial | Injected action | Observed from | Expected | Fails if | State after | Fail-closed |
|---|---|---|---|---|---|---|---|
| AN-1 | `Protected` | the interface carrying the default route is removed | O4 + O1 | the policy survives (it does not match on interfaces); traffic stops because there is no route | any prohibited egress | `Degraded` or `Blocked` | **yes** if confinement is unproven |

| AN-3 | `Protected` | connectivity is lost and restored | O4 + O1 | nothing escapes while connectivity is gone; the checks report INC, not failure | a check reporting a leak for a link failure; or `Protected` claimed while unverified | `Degraded` while unverified, then `Protected` | no |
| AN-4 | `Protected`, IPv4-only | an IPv6 address appears on the link | O1 | still no IPv6 egress from a protected uid | an IPv6 packet at the boundary | `Blocked` if a claim breaks | **yes** |
| AN-5 | `Protected` | a Wi-Fi/ethernet switch is simulated (new interface, new default route) | O4 + O1 | confined as before, without re-application | a prohibited packet from the new interface | unchanged | no |

## 8. Exemptions, in both directions

An exemption that passes because the test itself was privileged is not evidence. Each test therefore
runs the second direction as a **control** with an identity that must not obtain the same path.

| ID | Exemption | Direction A (must work) | Direction B (must not work) | Observed from |
|---|---|---|---|---|
| AE-1 | `system-user:tor` | a probe as the Tor uid reaches a destination outside | the same probe as an ordinary uid is confined | O1 |
| AE-2 | `system-user:tor` | the Tor uid's traffic is *not* redirected (it is Tor's own egress) | an ordinary uid's TCP **is** redirected | O4 |
| AE-3 | `dhcp-client` | a DHCP client can complete a lease | an ordinary uid cannot send UDP 67/68 | O1 |
| AE-4 | `system-user:dnscrypt-proxy` (DNS-lockdown mode) | the resolver uid reaches its resolvers | an ordinary uid cannot reach port 53 | O1/O3 |
| AE-5 | `system-user:dnscrypt-proxy` (Tor mode) | — | **the resolver uid is not exempt in Tor mode**; its only path is loopback, where the only proxy is Tor's SOCKS | O4 |
| AE-6 | LAN set (opt-in) | with the LAN exception, a LAN destination is reachable | without it, the same destination is not | O1 |
| AE-7 | The complete list | the exemption list reported matches the rules in the kernel, one by one, in both directions | an exemption in the kernel that the report does not list | O4 + O7 |
| AE-8 | Nothing else is exempt | — | the GUI, `core`, the verifier and ordinary uids cannot obtain any exempt path | O1 |

AE-5 is the one worth stating twice: in Tor mode the resolver has **no exemption at all**, and its
absence is the security property. If a test ever shows it reaching a resolver directly, that is a CPT.

## 10. Handling a defect

When adversarial testing finds one:

1. **Preserve the minimum reproduction** — the smallest arrangement of state, fault and traffic that
   still shows it, as a script or a test.
2. **Decide what is actually wrong**: the implementation, or the test oracle. Both are defects; the
   second one is more embarrassing and hides the first.
3. **Fix the cause**, not the symptom. A test relaxed to pass is a deleted test.
4. **Add a regression test that fails on the old behaviour** — verified by reverting the fix and
   watching it fail.
5. **Re-run the adversarial test** that found it.
6. **Re-run the whole v1 suite**, because a fix that breaks an unrelated claim has moved the problem.

A defect that is not reproducible as a test is recorded with its reproduction steps and left open.
